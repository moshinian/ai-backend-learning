## 主题

围绕平安产险后端开发工程师 JD 完成 Java 项目表达、MySQL 分区优化、可恢复分片任务、Redis 锁和 Spring Batch 停止机制的面试前压缩；面试后登记分布式事务 2PC / 3PC 知识缺口。

## 本次做了什么

1. 按 JD 将准备重点收敛到 Java、金融结算、数据库性能、任务可靠性和系统设计，不临时扩张 MongoDB、Spark、Spring Cloud 和消息产品细节。
2. 连续调整 60 秒自我介绍，突出四年 Java 后端、结算业务职责、性能与稳定性证据，并把 RAG / Agent 收敛为工程补充能力。
3. 将结算系统从内部业务名词提升到“服务对象、输入、公共主链路、输出、本人职责”层级，确认早期参与 2C 支付和 2B 预装，后期独立负责 2B 商推以及公共流水与核销。
4. 区分 N+1 批量查询、2C 支付订单物理分区和亿级流水分页索引三个不同性能案例，停止混用问题、方案和量化结果。
5. 重新确认 2C 支付订单表使用 `business_day` 日期分区，早期按月、后期按周；单次流水匹配通常查询一周数据，周分区改造将 100 万笔处理从约半小时恢复到约 8 分钟。
6. 区分数据库父任务抢占、Redis 功能级锁和业务幂等：数据库限制同名定时父任务；Redis 协调手工与定时两个入口；明细状态和批次事务保证不重复和续跑。
7. 还原分片任务状态、心跳、失败退出和父任务聚合：全部分片成功才成功；存在失败且没有执行中分片时失败；旧实例未退出前不启动新同名任务。
8. 重新确认项目使用过 Spring Batch。外部停止很可能通过 Spring Batch 停止 API 发出协作式停止信号，并同步自研任务状态为“停止中”，等待当前 Chunk 和所有分片退出后再允许重启。
9. 面试后记录分布式事务陌生问题：候选人记忆为“二级事务、三级事务”，当前只能推断可能指 2PC / 3PC，尚未学习，不把推断写成确定答案。

## 关键结论

1. 项目表达先建立系统全貌，再进入业务分支和实现细节；不同性能案例必须保持独立的问题、机制和指标。
2. “命中索引”不等于访问数据少；但历史上没有保留扫描行数时，只能确认分区方案、查询条件和性能结果，不能补写不存在的测量证据。
3. 数据库抢占和 Redis 锁是否重复，取决于保护范围。只保护同一条抢占 SQL 时可能重复；分别保护定时任务实例和手工 / 定时跨入口时职责不同。
4. Spring Batch 停止是协作式停止，不是强制杀线程；自研“停止中”状态负责业务侧可见性，框架执行状态负责真实运行收口。
5. 分片汇总字段能够表达固定分片结果，但状态字符串难以承载等待、运行、停止、超时、错误原因和并发更新；长期可演进为独立分片执行表。
6. 批次本地事务、Redis 锁、状态机、幂等和补偿属于任务可靠性与最终一致性机制，不能直接替代 2PC / 3PC 等分布式事务协议知识。
