## 4. 问题二：介绍你的 RAG + Agent 项目

> 请讲一下你做过的 AI 项目，你具体负责什么？

现场回答或目标回答：

> 项目起点来自荣耀财经部门的知识检索需求，由产品收集问题后交给开发认领。我在离职前完成了 RAG 初步搭建，但没有进入用户试用；离职后围绕同类场景继续个人工程实践，新增了 Rerank 和 Agent，所以我会明确区分公司阶段和个人后续阶段。

## 5. 问题三：RAG、Workflow 和 Agent 有什么区别

问题：

> 什么场景用 RAG，什么场景用 Workflow 或 Agent？

现场回答或目标回答：

> RAG 主要解决模型缺少企业知识的问题，通过检索证据增强生成。Workflow 的步骤和分支主要由开发者预先定义，确定性和可测试性更强，适合审批、资料处理等规则明确的流程。Agent 则让模型根据目标、上下文和工具结果动态决定下一步，适合路径不能完全预定义的任务。
>
> 我的选型原则是：能用固定流程解决的，不为了 Agent 而 Agent；需要动态工具选择时再引入 Agent。即使使用 Agent，权限、业务状态和高风险副作用也由 Java 后端或确定性工作流控制，模型负责理解和决策，不直接成为业务事实权威。

评价：

- 核心不是定义，而是选型边界。

改进版：

- 若追问 LangGraph，补充 State、Node、Edge、checkpoint、interrupt 和 human-in-the-loop；不要背完整 API。

后续任务：

- 与 `interview/ai-application-questions.md` 的框架边界保持一致。

## 6. 问题四：企业 API 如何接入 Agent 平台

问题：

> 如果把企业已有服务接入 AI 交互平台，你会怎么设计？

现场回答或目标回答：

> 我会先把企业 API 封装成边界明确的 Tool 或 Skill，定义工具名称、业务用途、输入输出 Schema、错误码、风险等级、权限和版本。模型只负责选择工具并生成候选参数，Java 平台负责用户身份、租户、权限、参数和业务状态校验。
>
> 查询类工具可以在限流、超时和审计约束下直接执行；创建、修改、删除等高风险操作先落成待确认 Action，用户确认后再次校验权限、状态和幂等键，再由受控节点执行。调用需要记录 runId、traceId、toolCallId、工具版本、参数摘要、结果状态和耗时。
>
> 外部调用超时时还要区分确定失败和结果未知。不能无脑重试写操作，而应使用稳定幂等键、状态机、查询确认、补偿任务或人工处理入口。这样才能把“模型会调用工具”升级为企业可治理的平台能力。

评价：

- 这是与兔展产品场景最贴合的高价值回答。
- Prompt 不是权限和安全边界。

改进版：

- 如果对方使用 MCP，说明 MCP 提供标准化发现与调用协议，但认证、授权、幂等和业务校验仍属于后端职责。

## 7. 问题五：AI 平台怎样做高可用和可扩展

问题：

> 如果平台流量增长或模型调用很慢，如何保证稳定性？

现场回答或目标回答：

> 我会先拆链路和目标，而不是直接说加机器。入口层明确 QPS、并发、P95 / P99、错误率和租户配额；Java API 尽量无状态化，通过注册发现和负载均衡扩展。模型、检索、工具和数据库分别设置超时、并发上限、隔离线程池、限流、熔断和降级，避免某个慢下游拖垮整个平台。
>
> 长任务不占用普通同步请求线程，而是创建 Run 后异步执行，通过事件流返回进度。Run、Step、Action、Event 和 Checkpoint 进入共享存储；数据库保存可恢复事实，Redis 或 MQ 用于队列、租约或跨实例实时广播。重复执行通过状态抢占和幂等键控制，实例异常后根据心跳和 Checkpoint 恢复。
>
> 验证时做阶梯压测，观察吞吐、P99、错误率、队列长度、数据库连接、线程池、模型 Token 速率和下游配额，并通过杀实例、网络超时和下游限流验证恢复、降级和重复执行率。

评价：

- 使用已有 Agent SSE 和结算长任务证据，不虚构现有项目已经完成多实例部署。

改进版：

- 被追问 Spring Cloud / Nacos 时，讲注册发现、配置和服务治理机制，同时说明个人尚无足够生产落地证据。

后续任务：

- 不在面试前扩张 Sentinel 或 Kubernetes 实现细节。

## 8. 问题六：你做过哪些性能优化和生产排障

问题：

> 讲一个 MySQL / MyBatis 性能优化或线上故障案例。

现场回答或目标回答：

首选性能案例：

> 流水任务最初按每笔流水查询支付订单，单条 SQL 不一定慢，但累计形成了 N+1 和大量数据库往返。我把订单号按每 1000 笔批量查询，并构建 Map 做内存匹配，使 100 万笔流水处理达到 8 分钟以内。这个案例的关键不是单条索引，而是先识别整体访问模型，再用批量化减少往返，并控制批次大小和内存代价。

首选排障案例：

> 对账池任务曾发生 OOM。我通过 Heap Dump 发现 ReconcileData 及关联对象保留内存超过 10GB，引用链指向 MyBatis 缓存。大批量一次性结果不适合被长生命周期缓存持有，所以关闭对应查询缓存，并在低内存环境做开关对照。修复上线后连续三个月没有再次发生 OOM。由于原代码已经无法复核，我不会进一步声称具体是一、二级缓存或某个 Mapper namespace 的问题。

评价：

- 两个案例分开讲；N+1 不与分区、分页案例混合。
- MyBatis 案例体现诊断证据和事实边界。

改进版：

- 面试官问 SQL 再讲 EXPLAIN、联合索引和尾页查询；不要一次堆四个性能案例。

后续任务：

- 根据追问选择一个案例深入，不主动穷举。

## 10. 问题八：你怎样使用 AI 编程工具

问题：

> 你平时如何使用大模型编程工具提高效率？

现场回答或目标回答：

> 我会把 AI 编程工具当成协作开发者，而不是直接采纳代码。需求阶段先让它帮助拆边界、列风险和验收条件；实现阶段用于检索调用链、生成局部代码和测试；排障阶段用于提出假设、关联日志和构造最小复现。最终仍由我核对真实代码、数据模型和依赖版本，并运行测试、静态检查和差异审查。
>
> 我现在的 RAG / Agent 工程就是持续使用 AI 工具协作开发的例子。这个过程也让我意识到一个风险：代码跑通不等于我已经掌握机制。颂拓面试时，我一度把项目已经实现的事件持久化和断线补发说成后续方案。之后我重新沿 Run、Step、Action、Event、事务边界和恢复链路做了代码级复盘。所以我认为高质量使用 AI 的标准不是生成多少代码，而是能否保留事实边界、完成验证，并把实现内化成自己能解释和维护的系统。

评价：

- 有真实收益，也主动说明 AI 协作的风险控制。

改进版：
