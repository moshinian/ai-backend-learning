## 2. 总体判断

这场面试不是因为项目经验不足而失去主导权，而是因为候选人没有稳定控制“系统全貌、本人职责、代表难点、技术机制”四个表达层级。面试官对结算领域不熟悉，多次要求先讲清系统像什么、单据怎样流转、本人负责哪里，再进入技术细节；候选人却在业务背景、分支细节、方案价值和零散技术点之间来回切换，导致面试官明确反馈“没有跟到你的节奏”“讲得太细”“没有 get 到难点”。

后半段 Java 问答进一步暴露两类知识缺口：一是无法稳定说出 Java 8 之后的代表特性；二是事务传播只能模糊描述 `REQUIRES_NEW`，不能说出名称、默认传播行为和代理执行过程。RocketMQ、数据库唯一约束和 AOP 用途有正确基础，但现场答案仍偏长，且经常先进入业务例子，再回答概念本身。

### 表现较好的部分

1. 能够说明荣耀云服务结算不是内部费用分摊，而是围绕游戏、会员、广告、预装等业务完成收入、分成、结算、ERP 入账和核销。
2. 最终能够把本人职责收敛到商推订单和公共流水核销两条主线，没有把整个二十人团队的工作全部归为个人成果。
3. RocketMQ 场景基本真实：用于异步结果通知、调用方与下游解耦，并缓冲集中回调带来的瞬时压力。
4. 幂等回答虽然顺序混乱，但提到了业务唯一字段、数据库唯一约束和条件更新三个有效机制。
5. AOP 在面试官再次收敛问题后，能够回答“围绕原方法增加日志、事务等横切能力”。
6. 面试反问覆盖了团队规模和入职后的工作方向，能够继续获取岗位信息。

### 主要短板

1. 项目介绍缺少固定缩放顺序。没有先用一两句话说明“系统为谁结算、输入输出是什么”，就不断补充业务分支和单据细节。
2. “做得最好的点”选择了对陌生听众门槛较高的冲销管道，又没有将难点压缩成状态机、反向补偿、重复纠错和跨系统一致性，最终被面试官判断为普通的“冲掉旧记录、写入新记录”。
3. 现场把冲销能力说成“我设计了一个冲销方法”，与既有证据中“早期已有部分实现，本人负责场景适配、缺陷修复和长期维护”的边界可能不一致。
4. 商推链路介绍仍然先讲规则、缓存和分页，后讲订单、结算单、辅账和下游，层级顺序倒置。
5. 面对 RAG 项目真实性追问时语气偏防御，没有先给出已经确认的时间线：产品收集财经部门需求、本人认领并完成 RAG 初步搭建、离职时尚未试用、离职后独立新增 Rerank 和 Agent。
6. RAG 与 Agent 两条链路没有在开头分开，导致面试官认为“知识库问答为什么需要人工确认”。
7. 不熟悉 Java 8 之后的代表版本能力，现场用“调用优化、回收更流畅”等模糊表述代替确定知识。
8. 不记得生产 Spring Boot 版本可以诚实保留，但没有给出“内部框架封装、准确版本以 parent / BOM 为准”的简短边界后立即停止。
9. AOP 第一次回答展开了推送、幂等、超时和下游查询，面试官再次明确指出没有跟上节奏。
10. 事务传播不能说出 `REQUIRED`、`REQUIRES_NEW` 等准确名称，也没有解释事务拦截器如何根据传播属性加入、挂起或创建事务。

### 问题 3：你做得最好的部分是什么，技术难点在哪里

**面试官原问题**

> 你写了很多点，哪个点做得最好？这个方案的技术难点和吸引点在哪里？

**我的现场回答**

> 选择流水冲销管道，说明上游金额或数据错误时，旧流水可能已进入 ERP 和核销阶段，需要生成反向辅账、释放订单并让新流水重新处理。反复强调这是端到端方案、需要适配不同分支，并补充通过接口继承、类型匹配实例和配置实现扩展。

**评价**

- 评分：4/10。
- 回答正确的部分：能够意识到它不是单条 SQL，而是跨 ERP 和核销阶段的业务补偿；提到了多次重推、分支抽象和策略实现。
- 主要问题：没有先给出状态模型和不变量，面试官只能将它理解为“冲掉 9 元，再写 10 元”；“方案设计”“持续适配”“综合应用”等抽象词重复出现，但没有提供可验证的技术约束。

**更好的回答**

> 这条链路最难的不是插入一条负数记录，而是原流水可能停在不同状态：只入接口表、已生成辅账、已在 ERP 入账，或者已经与订单核销。系统必须根据当前状态选择不同的反向补偿，而且补偿完成前不能让新批次重复生效。
>
> 实现上，我们用原批次号关联多次纠错批次，以状态机判断原数据推进阶段；已入账的流水生成金额相反的冲销辅账，已核销的数据先生成撤核销辅账，ERP 回写成功后再释放订单回到未对账池。任务失败通过原业务标识重试，下游配合幂等。我的实际贡献是后续业务分支适配、问题修复和长期维护，不把早期已有管道说成完全从零设计。

**需要补充学习**

1. 如果对方要求“明确技术难点”，优先选择证据更清楚的 N+1 批处理、可恢复任务或 ERP 凭证 ID 碰撞案例。
2. 冲销故事必须先讲状态、不变量和补偿动作，再讲策略扩展。

### 问题 4：商推订单到结算的完整链路是什么

**我的现场回答**

> 说明上游商推平台接收大数据预处理结果，再将订单通过 API 推送到结算系统。订单包含 CP、交易日期、金额、机型和 APP 等信息；系统幂等接收后批处理，匹配合同和主数据，形成结算数据，再生成结算单和辅账。结算单进入结算中心，应付场景还包含确认回调、盖章和邮件。自然账期为一个月，但会提前处理和收敛部分数据。

**评价**

- 评分：5/10。
- 回答正确的部分：经过多次追问后，输入、核心单据、下游和账期基本能够重建。

- 待确认事实：现场提到“一天百万级订单通过 API 推送”，当前简历只确认百万级批处理，不能在未核实前转为长期事实。

**更好的回答**

> 商推平台是上游，它把已经计算好的广告消耗订单通过接口推给我们。我们先按业务唯一键幂等接收，再匹配客户、合同和结算规则。核心结果分两路：业务结算数据按客户和账期收敛成结算单，财务数据生成会计辅账并推送 ERP。结算单交给结算中心完成收付款流程，辅账回写后进入后续核销。自然账期是一个月，但月中可以先完成预处理，月结时只做最终收敛，避免把整月数据集中到一天处理。本人负责订单接入和处理链路，并复用公共结算单与辅账能力。

**需要补充学习**

1. 先画单据骨架，再回答规则、性能和扩展实现。

### 问题 8：上游接口幂等怎么做

### 问题 9：AOP 主要用来做什么

**面试官原问题**

**我的现场回答**

> 第一轮从事务例子展开到推送记录、网络超时、幂等查询和下游重试。面试官重新收敛后，回答 AOP 是在原方法外增加事务、日志和配置检查等业务增强。

- 评分：5/10。

**更好的回答**

> AOP 用于把事务、日志、权限、缓存、监控等横切逻辑从业务方法中抽离。Spring 通常为 Bean 创建 JDK 动态代理或 CGLIB 代理，外部调用先进入拦截器链，再执行目标方法。以 `@Transactional` 为例，事务拦截器在方法前开启或加入事务，成功后提交，符合回滚规则的异常则回滚。AOP 适合稳定的横切能力，不适合隐藏核心业务流程。

### 问题 10：事务传播机制及其 AOP 实现

**面试官原问题**

> 介绍事务传播机制，以及它在 AOP 里面怎么实现。

**我的现场回答**

> 只记得一种“新建事务”，但无法说出 `REQUIRES_NEW`；描述外层大事务调用一个独立小事务，小事务异常只处理当前事务，并补充 AOP 依赖 Spring Bean 类与类之间的调用。

**评价**

- 评分：3/10。
- 回答正确的部分：意识到独立事务与外层事务不同，也知道必须经过 Spring Bean 代理调用。
- 主要问题：没有说默认 `REQUIRED`，没有准确说出 `REQUIRES_NEW`，也没有解释加入、挂起、新建、提交和回滚；“小事务异常只影响自己”还取决于异常是否继续抛给外层以及外层是否捕获。

**更好的回答**

> Spring 默认传播行为是 `REQUIRED`：当前有事务就加入，没有就新建。`REQUIRES_NEW` 会挂起外层事务并创建独立事务，内层可以独立提交或回滚；但如果内层异常继续抛到外层，外层仍可能因为该异常回滚。`NESTED` 通常在已有事务内通过保存点实现局部回滚，它和独立事务不同。
>
> 实现上，Spring 在 Bean 后置处理阶段为带事务规则的方法创建代理。外部调用进入 `TransactionInterceptor` 后，它读取事务属性，通过 `PlatformTransactionManager` 判断加入现有事务、挂起事务还是创建新事务；目标方法成功则提交，异常则按 rollback rule 回滚。内部 `this` 调用绕过代理，因此事务传播也不会被拦截器重新应用。

**需要补充学习**

1. 先掌握 `REQUIRED`、`REQUIRES_NEW`、`NESTED` 三种高频传播。
2. 再了解 `SUPPORTS`、`MANDATORY`、`NOT_SUPPORTED`、`NEVER` 的语义。
