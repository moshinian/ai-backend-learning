## 2. 岗位匹配判断

这不是偏模型训练的算法岗，而是把 Agent 做成稳定生产服务的后端工程岗位。候选人的 Java 后端、数据库、任务可靠性、幂等、缓存、MQ 和生产排障经验与岗位目标高度相关，个人 RAG / Agent 项目又提供了 AI 工程迁移证据。

本场体现出的优势：

1. 能先澄清系统边界，再讨论 Java、Python、前端和云平台分别负责什么。
2. 能把数据库状态、唯一 ID、断线补发、心跳接管、压测和故障演练串成工程链路。
3. MySQL 性能、批处理可靠性和线上问题排查有真实生产证据。
4. 遇到 Python 部署、容器底层和本地模型部署等不熟悉领域时，没有虚构生产经验。

本场暴露出的主要短板：

1. 对自己项目已经实现的 SSE 事件持久化与恢复链路认识不完整，现场把既有实现说成了建议方案。
2. 容易把 Step 级事件流、Token 级流式生成、事件持久化和多实例广播混在一起。
3. Python 多实例部署、容器沙箱隔离和模型工程化部署缺少可落地的技术细节。
4. 长期记忆、自进化、长任务校验与工具选择质量的回答仍偏临时方案，缺少稳定的状态模型和评测闭环。

本场不改变“Java 后端主线 + AI 应用工程补充”的长期定位。该岗位恰好需要用生产后端能力补 Agent Runtime，因此值得进行短周期专项补强。

## 3. 现场问题复盘

### 问题 1：个人 Agent 系统最有挑战的部分是什么，SSE 有什么缺陷

**现场回答**

候选人指出当前只能按步骤返回，不能像 ChatGPT 一样逐 Token 输出；随后建议增加状态表、Run 唯一 ID 和 `Last-Event-ID` 补发机制。

**评价**

问题判断方向是对的，但项目事实表达失真。个人 `rag-system` 已经存在 `agent_run`、`agent_run_step`、`agent_action`、`agent_run_event`、Java 到 Python 的运行时 SSE，以及 Java 到前端的业务 SSE；同时已经实现完整事件持久化、事务提交后发布、`Last-Event-ID` 补发、心跳和孤儿 Run 恢复。

真正尚未完成的是：Token 级流式、多实例共享广播、用户主动取消，以及完整生产认证、指标与告警。不能把“已经实现的 Step 级可恢复事件流”说成“尚未实现状态表”。

**改进版**

> 我的 Agent 流式链路分两段。Python Runtime 通过 SSE 向 Java 返回步骤事件，Java 先把完整业务事件写入 `agent_run_event`，事务提交后再发布给前端；前端断线重连时携带 `Last-Event-ID`，Java 先补发数据库里缺失的事件，再继续实时订阅。Run 表示一次完整执行，Step 是可观察阶段，Action 是需要确认的业务动作，Event 是按 Run 单调排序的流式事实。当前已经做到 Step 级事件持久化和断线恢复，但还不是逐 Token 输出，多实例广播目前也仍需要 Redis Pub/Sub 或 MQ 之类的共享通道。

**后续任务**

1. 以 `backend/distributed-system/agent-sse-event-stream-and-recovery.md` 为准完成 60 至 90 秒闭卷口述。
2. 回答时固定区分事件粒度、数据库写入粒度、断线恢复和多实例广播四个问题。

### 问题 2：数据库性能与 AI 检索如何优化

**现场回答**

候选人列举分页优化、N+1、MyBatis 缓存 OOM、任务抢占和分库分表，并提到 PostgreSQL 向量能力及可引入会议纪要中的 `Bn25`。

**评价**

传统后端部分有真实经验。检索部分应校正为 BM25，并区分当前事实和后续方向：个人项目已有 PostgreSQL 全文检索 / 模糊检索、向量检索、Hybrid RRF 与 Rerank，但不能把 BM25 写成当前已落地实现。

**改进版**

> 我会先拆成召回、融合、排序和生成四层定位问题。当前项目用 PostgreSQL 承载业务数据和向量检索，并组合关键词召回、向量召回、RRF 融合和 Rerank。中文关键词效果不足时，BM25、中文分词和领域词典是可验证方向，但要通过私有测试集比较 Recall@K、MRR、最终回答命中率和时延，不能只因为算法名称更先进就替换。

### 问题 3：模型多语言能力不足时如何处理

**现场回答**

候选人建议用轻量翻译工具或脚本先规整输入，减少直接使用大模型的成本。

**评价**

工程降本方向合理，但“全部翻译后再处理”可能丢失运动术语、地名、单位和用户原意。

**改进版**

> 我会先做语言识别、编码和单位规范化，同时保留原文；优先验证多语言 Embedding 和目标模型的原生能力，再针对弱语言增加术语词典或翻译回退。翻译结果、原文和模型版本都进入评测集，比较任务正确率、术语保真度、时延和成本，而不是默认所有输入都先翻译。

### 问题 4：MCP / Skill 如何做版本控制，为什么显式版本后效果仍不好

**现场回答**

候选人建议在 Schema 中增加版本号，由前端强制指定或系统自动选择最优版本；之后判断问题还可能来自工具描述或用户问题不规范。

**评价**

版本号解决的是兼容性和可复现性，不直接保证模型选对工具。还要区分 MCP 协议版本、工具 Schema 版本、Skill / Prompt 版本、模型版本，以及模型的工具选择质量。

**改进版**

> 我会先判断是兼容性故障还是选择质量故障。兼容性通过显式工具版本、Schema 校验、契约测试、灰度和回滚处理；选择质量则要检查工具名称和描述是否重叠、参数约束是否清楚、候选工具是否过多、示例是否具有区分度，并用固定评测集记录工具选择准确率和参数正确率。版本号让一次调用可重放，但不会自动让模型做出正确决策。

### 问题 5：个人记忆如何自进化，长任务跑偏后如何检测

**现场回答**

候选人提出时间戳、版本号、独立预处理模块、高能力模型短时校验和上下文压缩。

**评价**

已经识别时序冲突、校验能力和成本之间的矛盾，但还没有形成可验证的记忆数据模型和长任务控制闭环。

**改进版**

> 记忆不应直接把每轮总结覆盖成唯一真相。我会保留来源、主体、有效时间、写入时间、置信度和版本；新旧事实冲突时先并存并标记，再由确定性规则、用户确认或离线整理任务形成新的有效快照。长任务则在计划、工具调用和关键状态转换处设置检查点，用 Schema、业务不变量、权限和预算做确定性校验；只在语义一致性难以硬编码时调用独立 Judge，并抽样或按风险触发，避免全程双模型带来的 Token 成本。

**现场回答**

候选人按监控平台和服务器现场两条线排查，提到慢查询、内存、Linux 命令和上游幂等异常。

**评价**

### 问题 7：FastAPI 单实例如何改造成多实例，如何压测和恢复

**现场回答**

候选人先确认架构边界，再提出复用现有流量平台、Kubernetes 多实例、SLA / QPS 基线、单实例压测、多实例扩展、主动杀实例和状态表恢复。

**评价**

容量与故障演练方法正确，但 Python 部署细节不够具体。需要补齐无状态 API、共享状态、任务归属、SSE 跨实例广播和优雅退出。

**改进版**

> 先把 FastAPI 实例改成无状态入口，把 Run、事件和 Checkpoint 放进 PostgreSQL，把队列、租约或广播放进 Redis / MQ；Kubernetes Deployment 和 Service 负责多副本与路由，readiness / liveness / startup probe 区分是否接流量和是否需要重启。实例退出时先摘流量、停止领取新任务、续跑或释放任务租约。SSE 若可能重连到另一实例，实时事件必须走共享广播通道，数据库事件表负责补发。压测先定并发、P95 / P99、错误率、Token 速率和下游配额，再验证扩容、限流以及杀实例后的恢复时间和重复执行率。

### 问题 8：本地模型、MCP 工具和 Docker 多用户隔离经验

**现场回答**

候选人如实说明本地模型和容器底层经验有限；MCP 部分称 Java 扫描注解进行工具权限和版本控制，供 Python 调用。

**评价**

诚实边界是正确的，但“Java 扫描注解”不是当前个人项目实现。当前代码以 `McpTool` 接口、`McpToolRegistry` 和协议 `annotations` 元数据组织工具；权限仍要由确定性业务层校验，不能把 MCP `annotations` 当成认证授权。

容器沙箱的最小入口包括：每任务或每用户隔离、非 root、只读根文件系统、最小挂载、网络策略、CPU / 内存 / PID / 时间限制、镜像和依赖白名单、临时凭证、审计与销毁。更强不可信代码隔离可评估 gVisor、Kata Containers 或独立沙箱服务，但当前没有生产实践。

### 问题 9：Transformer 的 QKV 与 Decoder 流程

**现场回答**

自动纪要记录为“权重分配与记忆，Attention 后线性归一化得到字词概率矩阵”。原话可能经过压缩，无法确认完整度。

**改进版**

> 每个 Token 的表示经过线性变换得到 Q、K、V。当前 Token 的 Q 与上下文 K 做点积并除以 `sqrt(d_k)`，经过 Softmax 得到注意力权重，再对 V 加权求和；多头结果拼接后进入输出投影，并通过残差、归一化和前馈网络继续变换。Decoder 最后的隐藏状态经过线性层得到词表 logits，再按解码策略产生下一个 Token。QKV 不宜直接简化成长期记忆，长期记忆通常需要外部存储和检索机制。
