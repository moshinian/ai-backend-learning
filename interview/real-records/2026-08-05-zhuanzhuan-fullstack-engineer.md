## 3. 逐题复盘

### 问题 1：将所有 a 通过相邻交换移动到左侧

**面试官原问题**

> 输入一个只包含 `a` 和 `b` 的字符串，通过相邻交换把所有 `a` 移到左侧，在 15 分钟内独立完成，不允许 AI 代写。

**屏幕共享草稿**

候选人使用 `ABABABABBB` 等样例，记录第 x 个 A 的当前位置 X，并得到 `delta = X - x`，随后计划用 `HashMap<Integer, Integer>` 保存 A 的顺位和当前位置，再累加所有位置差。候选人补充的核心草稿为：

```text
顺位第x的A，在当前字符串第X的位置
位置差X-x

hashMap<Integer, Integer> map;
countA = 0
step

for i from 0 to length(s):
    if (s.charAt(i) == 'A') {
        map.put(countA, i);
        countA++;
    }

for (key, value) from map:
    step += value - key
```

**评价**

- 正确部分：第 x 个 `a` 最终应位于下标 x，当前位置为 X 时需要左移 `X - x`，总和就是最少相邻交换次数。该推导与累计每个 `a` 前面的 `b` 数量等价。
- 主要问题：Map 不影响正确性，但完全不必要；题目可以一遍扫描、`O(1)` 额外空间完成。草稿没有形成合法 Java，字符大小写与题目不一致，空串判断仍是伪代码，也没有处理交换次数可能超过 `int` 的边界。
- 面试结论边界：会议助手概括为“懂逻辑但写不出代码”过于粗糙。更准确的说法是“核心公式正确，但没有在限时内完成工程化收敛”。

**改进版**

> 第 `countA` 个 a 最终应该在下标 `countA`。扫描到下标 i 的 a 时，它前面多出来的位置都是需要跨过的 b，所以累加 `i - countA`，然后 `countA++`。一遍扫描即可。

```java
public static long minAdjacentSwaps(String s) {
    if (s == null || s.isEmpty()) {
        return 0L;
    }

    long steps = 0L;
    int countA = 0;
    for (int i = 0; i < s.length(); i++) {
        if (s.charAt(i) == 'a') {
            steps += i - countA;
            countA++;
        }
    }
    return steps;
}
```

### 问题 2：MySQL 分区与跨时间查询

**面试官原问题**

> 单日订单量很大时，当前分区和索引方案如何工作？跨月查询是否仍然足够快？为什么没有垂直拆表或直接分库分表？

**现场回答摘要**

候选人介绍按业务日做 Range 分区、联合索引和基于递增 ID 的游标分批查询；跨时间查询依赖分区裁剪，只扫描命中的分区。被追问跨月查询时，候选人说明当前是内部系统，已有性能基线能够满足；若变成 C 端场景，需要重新考虑分库分表等扩展方案。

**评价**

- 正确部分：能够说明方案必须结合查询窗口和内部性能基线，分区裁剪可以排除无关分区。
- 主要问题：分区表仍是一张逻辑表，不能表述成“把单表数据控制在一周”；跨月查询即使发生分区裁剪，也仍要处理所有命中的分区和数据。分区优化案例、亿级尾页分页案例和 N+1 案例必须继续分开，不能相互替代性能证据。
- 事实边界：会议摘要中的“单表日订单数百万、控制在一周、跨月 3 秒”等口径需要与既有项目文档逐项核对，不直接写入简历或正式项目事实。

**改进版**

> 当前方案针对内部批处理的一周查询窗口，通过按业务日 Range 分区让查询只命中相关分区，再配合联合索引和游标分批降低单次处理成本。分区裁剪只能减少无关分区，跨几个月查询仍会扫描命中的历史范围。如果访问模式变成 C 端用户历史订单，我不会直接沿用批处理方案，而会重新按用户列表和订单详情设计路由、分页、冷热分层，容量不足时再进入分库分表。

### 问题 3：ToC 用户历史订单怎么设计

**面试官原问题**

> 类似电商的用户订单表，在单表不足、需要查询历史订单时怎么设计？如果允许分库分表，你会怎么拆？

**现场回答摘要**

候选人先确认用户查询历史订单的场景；在限制分库分表时提出用小表保存键值关联、大表读取详情；进入分库分表讨论后，继续询问现有架构和业务维度，随后提出通过配置项或管理表统一维护多表路由，但没有完整说明分片键和读写路径。

**评价**

- 正确部分：知道先确认查询场景，也意识到列表索引与详情存储可以分离，路由需要由中间层统一管理。
- 主要问题：没有先区分用户订单列表、订单详情和运营跨用户查询；没有给出默认的 `user_id` 分片方向、`order_id` 点查路由、游标分页、历史冷热、热点和扩容代价。面试官要求独立设计后仍持续探询对方架构，削弱了方案 ownership。

**改进版**

> 我先假设核心链路是用户查看自己的订单列表和订单详情。列表优先按 `user_id` 路由，让单个用户查询落到一个逻辑分片，并使用时间加订单 ID 的游标分页；详情通过包含路由信息的订单 ID，或单独的订单路由索引定位。历史订单按时间做冷热分层，运营跨用户查询走独立搜索或分析链路，避免在线库跨所有分片聚合。只有单库写入、容量或维护边界不足时才物理分库；扩容需要提前设计逻辑分片和迁移过程。

### 问题 4：对账任务重复、6 小时 Redis 锁与停止恢复

**面试官原问题**

> 明细插入和状态更新不在同一事务导致重复后，如何重构？为什么 Redis 锁要 6 小时？任务宕机或运行过长怎么办？

**现场回答摘要**

候选人说明通过明细级状态和标志位支持可重复运行；Redis 锁用于阻止同名定时任务与人工入口同时触发，6 小时来自业务最大执行时间。面对宕机和长锁风险，又补充数据库抢占、心跳、多分片、软停止和人工排查重跑。

**评价**

- 正确部分：能够区分跨入口互斥与数据库任务状态，也能讲到协作式停止、心跳和失败恢复。
- 主要问题：先用“标志位”解释防重仍不够，需要补充事务、条件更新、唯一约束和业务幂等。面对 6 小时锁追问，没有先回答固定 TTL 自身的两条时间线：宕机后可能持续阻塞到 TTL；任务超过 TTL 时可能提前失锁但旧实例仍在执行。
- 术语边界：如果 Redis Key 有固定 TTL，实例宕机通常不是永久死锁，而是最长阻塞到 TTL；会议助手和面试官口语中的“死锁”应校准为长时间不可用或锁租约边界。

**改进版**

> 这把 Redis 锁只负责协调手工和定时两个入口，不是数据只处理一次的最终保证。固定 6 小时 TTL 可以防永久锁，但实例很早宕机会让入口白等，任务超过 6 小时又可能提前失锁。因此更合理的是用短锁保护数据库抢占，长期执行权交给 owner token、租约和心跳；数据正确性依赖条件状态、唯一约束、批次事务和明细幂等。业务 6 小时上限用于告警与停止，不应直接等同于锁租约。

**后续任务**

1. 回流 `BL-002` 与 `mistakes/distributed/redis-lock.md`。

**面试官原问题**

> RAG 出现幻觉或答非所问时，怎样进行全链路排查？

**现场回答摘要**

候选人从最终答案向上排查，先判断排序后的证据是否支持问题，再追到召回、Embedding 和 Chunk；同时提到 Recall@K、NDCG、答案准确性和忠实度。

**评价**

- 这是本场相对稳定的回答，具备检索、排序、生成分层意识。
- 会议摘要中的 `record K` 应校准为 `Recall@K`。
- 仍可补充 Query rewrite、权限过滤、引用一致性、模型输入是否包含正确证据，以及离线评测与线上问题回放的对应关系。

**改进版**

> 先保存原问题、改写 Query、召回候选、Rerank 结果、最终 Prompt 和模型答案。若正确证据已经进入 Prompt 但答案错误，重点排查生成与忠实度；若正确证据召回但排序靠后，排查融合和 Rerank；若未召回，继续排查 Query、权限过滤、Embedding、Chunk 和索引。离线分别看 Recall@K、MRR / NDCG 和答案忠实度，线上使用真实失败样本回放。
