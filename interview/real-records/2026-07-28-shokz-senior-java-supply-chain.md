## 3. 逐题复盘

### 问题 1：ERP 数据集成如何保证幂等

**面试官原问题**

> ERP 数据集成如何做幂等？

**我的现场回答**

> 先查表确认状态，再更新入库。面试官指出查询和更新不具备原子性。我解释系统通过现有处理模式保证同一时刻只会有一个实例处理一个批次，因此查询和更新不会发生冲突；我也理解对方担心的是查询后数据被其他实例或方法更新，导致后续状态更新错误。

**评价**

- 评分：部分成立，但论证不够完整。
- 回答正确的部分：如果系统确实通过不可绕过的批次分片、任务抢占或互斥机制保证单批次只有一个执行者，并发窗口在当前业务约束下可能不会出现。
- 主要问题：“先查再写”本身仍不是原子保证；单执行者解决并发碰撞，不自动解决任务重试、人工补偿、重复文件等先后重复执行。现场所说“处理模式”过于抽象，没有交代处理权存在哪里、锁失效怎么办、是否还有其他入口。

**改进版**

> 您说得对，单纯先查再写本身不具备原子性。我们当前链路先通过批次级处理权保证同一批次只有一个执行者，查询主要用于判断业务分支；如果要在数据库层做最终兜底，批次状态应使用带原状态条件的 UPDATE，通过影响行数判断是否抢占成功，明细数据还要使用稳定业务键和唯一约束防止重复写入。这样即使发生重试，也不会因为先查后写的窗口造成重复生效。

如果本数据集成模块没有实际落地数据库条件抢占或唯一约束，面试时只能将后半段表述为改进方案，不能移植其他任务的实现当作本模块生产事实。

**后续任务**

1. 用“单执行者、原子条件、业务唯一键、重试”四个入口重新回答。
2. 与结算系统已有数据库状态抢占、Redis 执行标识锁、批次事务和 Checkpoint 事实对照，但保持模块边界。

### 问题 2：冷热分离后 DELETE 是否释放空间

**面试官原问题**

> 冷库 INSERT、热库 DELETE 以后，本地 MySQL 的 DELETE 不会释放空间；你们为什么可以？

**我的现场回答**

> 我们使用的是集群 MySQL，现网观察到 DELETE 后存储占用确实下降，可能差异来自这里。面试官继续问集群如何做到，我说明 MySQL 治理不是自己的职责，底层机制了解不多。

**评价**

- 评分：生产现象可以保留，但机制归因不成立。
- 回答正确的部分：能够给出实际使用环境和观测结果，并在不知道底层实现时停止扩张。
- 主要问题：“释放内存”不是准确口径；需要区分删除记录、InnoDB 页可复用、`.ibd` 文件缩小、操作系统磁盘回收和云平台存储统计。仅凭“集群 MySQL”不能解释物理空间回收。

**改进版**

> 我们现网确实观察到历史数据迁移并删除后，云平台显示的存储占用下降，这是我能确认的生产事实。但原生 InnoDB 普通 DELETE 通常只是让部分页空间可复用，不等于 ibd 文件立即缩小并归还操作系统。现网差异可能来自分区回收、表重建、云平台自动整理或统计口径，具体机制不是我负责的，不能直接归因于集群 MySQL，需要结合版本、表空间配置和平台能力验证。

**后续任务**

1. 本地验证 `DELETE`、`TRUNCATE`、`OPTIMIZE TABLE` 在独立表空间下的文件大小和可复用空间差异。
2. 后续确认原项目是否使用分区删除、自动碎片整理或云数据库存储缩容能力。

### 问题 3：如何保证 RAG 回答与用户问题对应

**面试官原问题**

> 怎么保证大模型回答的内容和用户的问题是对应的？

**我的现场回答**

> 第一反应是通过 `trace_id` 和 `session_id` 保存用户请求、会话和模型交互。面试官澄清后，回答将用户问题做 Embedding，与 pgvector 做语义匹配获得候选 TopK；同时使用 PostgreSQL 做精准词匹配，对两路结果融合后进入 Rerank，再取 TopK 组装 Prompt，由大模型完成回答和拒答。

**评价**

- 评分：第一次理解偏题，澄清后的工程链路合格。
- 回答正确的部分：能够覆盖语义召回、精准词召回、融合、二阶段重排、Prompt 组装和拒答。
- 主要问题：`trace_id` 和 `session_id` 解决可追溯性与会话关联，不保证语义相关；还需要区分“正确证据是否进入 TopK”和“模型是否忠实使用证据”。项目事实边界也必须稳定。

**改进版**

> 我会把这个问题拆成检索相关性和生成忠实性两层。检索层先用 pgvector 做语义召回，再用 PostgreSQL 全文或关键词检索补充编号、专有名词等精确匹配，通过加权或 RRF 融合候选；独立分支 Demo 中尝试接入过 Rerank 做二阶段精排，但还不是正式主链路。生成层把高相关证据连同来源组装进 Prompt，约束模型基于证据回答，证据不足时拒答，并用 Recall@K、MRR、NDCG、答案正确性、faithfulness 和引用准确性做离线评测。

### 问题 4：如何理解 Spring Bean 生命周期

**面试官原问题**

> 你怎么理解 Spring Bean 的生命周期？

**我的现场回答**

> 我知道单例和多例 Bean。单例 Bean 在 Spring Boot 服务启动时创建，随服务器关闭而销毁；多例 Bean 在调用时创建，需要手工销毁。

**评价**

- 评分：核心边界基本正确，但回答的是作用域和创建 / 销毁时机，没有完整展开生命周期。
- 回答正确的部分：默认非懒加载 singleton 通常在容器初始化时创建，容器关闭时执行受管理的销毁回调；prototype 每次获取通常创建新实例，Spring 不完整管理其销毁阶段。
- 主要问题：“手工销毁多例 Bean”应更准确地说成“Spring 不自动调用 prototype 的销毁回调；其持有的外部资源由使用方释放”，对象本身仍由 JVM GC。还缺实例化、依赖注入、扩展回调和初始化阶段。

**改进版**

> Spring Bean 生命周期可以先压缩成创建、注入、增强、销毁四段。容器根据 BeanDefinition 实例化对象并完成属性填充，然后执行 Aware 回调、BeanPostProcessor 前置处理和 `@PostConstruct` 等初始化回调，再经过后置处理，必要时暴露代理对象。默认非懒加载 singleton 通常随容器初始化并在容器关闭时执行销毁回调；prototype 每次获取时创建，Spring 负责创建和初始化，但通常不负责调用销毁回调。

**后续任务**

1. 不背孤立接口名，先用“创建、注入、增强、销毁”恢复主线。
2. 再补 Aware、BeanPostProcessor、初始化和代理四个追问入口。
