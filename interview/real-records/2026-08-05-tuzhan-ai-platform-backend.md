## 2. 总体判断

### 表现较好的部分

1. 自我介绍能把四年 Java 生产后端、结算系统性能可靠性和 RAG / Agent 工程放在一条岗位主线上。

### 主要短板

1. 多轮 RAG 没有建立“先改写独立 Query，再检索”的入口，把会话历史、生成 Prompt、Agent 和 MCP 混在一起。
2. Agent 系统设计先讲 QPS、租户、状态表和监控，没有先给出 Model、Messages、Tools、tool loop、权限执行和 ToolMessage 的最小 Harness。
3. 个人项目实际已有单 Agent 工具循环和工具注册，但简历与口述只呈现零散组件；同时长期记忆、Skill 管理、多 Agent / Router 和代码沙箱确实尚未实现。
4. 现场新增了 Word、几千份文档、千万字符、Embedding 约 300ms、LLM 约 1000ms、本地模型与内部模型平台等说法，当前仓库证据不足，存在事实漂移风险。
5. 联合索引回答停留在口诀，不能区分扫描区间、覆盖索引、回表和 ICP。
6. 计算机视觉实习中的 YOLOv3、Faster R-CNN、ResNet、分类网络和样本量说法不够稳定，与当前简历表述需要重新核对。

### 问题 3：为什么选 pgvector，规模和延迟如何

**面试官原问题**

> 为什么使用 pgvector？文档和 Chunk 数据量多大？查询回复多久？模型怎么部署？

**现场回答**

候选人认为 PostgreSQL 可以同时承载业务状态、权限、SQL 查询和向量检索，当前内部知识库规模不大；随后给出几千份文档、千万字符、Embedding 约 300ms、LLM 约 1000ms，并讲到早期本地模型和荣耀内部模型平台。

**评价**

- 回答正确的部分：中小规模场景中使用 PostgreSQL + pgvector，可以减少独立向量数据库带来的系统复杂度，并便于事务、元数据过滤和业务数据共存。
- 主要问题：不能泛化为“纯向量数据库不适合状态和权限”；专业向量库也能保存元数据或与业务库组合，只是架构成本和能力取舍不同。

**更好的回答**

> 当前规模不大，而且知识库、文档状态、权限元数据和向量需要频繁关联，所以选择 PostgreSQL + pgvector，主要收益是架构简单、事务和过滤方便。代价是向量规模、索引类型、水平扩展和专业检索能力不一定优于独立向量数据库。具体规模和延迟我只使用保留过的测量数据；没有监控证据时，不给精确数字。

### 问题 9：联合索引与 ICP

**面试官原问题**

> `SELECT A,B,C FROM T WHERE A=1 AND B>2 AND C=3` 怎么建索引？`(A,B,C)` 哪些字段用于索引？C 是否使用索引下推？

**现场回答**

候选人先询问 A 与 C 的区分度，在 A 区分度更高的前提下给出 `(A,C,B)`；解释时提到物理分区和扫描层次。随后把 `(A,B,C)` 判断为不行，再改为 A、B 使用而 C 不使用，并明确不了解 ICP。

**评价**

- 回答正确的部分：知道两个等值条件应尽量放在范围条件之前，`(A,C,B)` 能形成 A、C 等值前缀后再使用 B 范围；也意识到只查询 A、B、C 可以考虑覆盖索引。
- 主要问题：`(A,B,C)` 不是完全不可用；A 等值和 B 范围仍可构造扫描区间，C 通常不能继续缩小区间，但仍在索引记录中。没有区分搜索区间、过滤和回表。
- 面试官解释边界：面试官用“C 在二级索引中先过滤，从而减少回表”讲 ICP，作为概念入口基本成立；但对本题 `SELECT A,B,C` 且索引正是 `(A,B,C)`，查询可能由覆盖索引直接返回，不一定存在读取完整表行的回表过程。MySQL 官方文档说明 ICP 主要在需要读取完整行时先用索引列过滤，以减少完整行读取；实际要看 `EXPLAIN` 的 `Using index` 与 `Using index condition`。

**更好的回答**

> 如果只针对这条查询，我倾向 `(A,C,B)`：A 和 C 是等值条件，可以形成更完整的等值前缀，再对 B 做范围扫描；A 与 C 的先后还要结合选择性和其他查询复用。`(A,B,C)` 也能使用 A 和 B 构造扫描区间，只是范围条件 B 之后的 C 通常不能继续缩小该区间。C 仍可在索引记录上过滤。ICP 是在需要完整行时把只依赖索引列的条件下推到存储引擎，先过滤再决定是否读整行；而本题只查询 A、B、C，可能本身就是覆盖索引，需要以 EXPLAIN 为准。

**需要补充学习**

1. `BL-030` 与 `mistakes/database/composite-index-range-and-icp.md`。

## 5. 跨题错误模式

1. 复杂问题一来先讲后端可靠性，未先给出被问系统的最小功能闭环。
2. 对自己项目的代码证据不熟，导致已经实现的 Agent loop、Tool Registry 和风险分流未形成架构表达。
3. 为了让回答更完整，现场补入了没有保留证据的数据规模、延迟、文件类型和模型部署事实。
4. 使用“走不走索引、带上上下文、做成 Agent”等大词，没有拆成搜索区间、Query、Prompt、State、ToolMessage 等精确对象。
5. 被质疑项目深度后倾向立即辩护，应该先承认真实缺口，再用代码证据说明当前已实现边界。
6. 职业经历回答过度还原负面情绪，没有把重点放在能力积累和当前主动选择。
