# 万级 QPS 容量设计与高并发治理

关联任务：`BL-016`

## 1. 本质

万级 QPS 设计的本质不是给系统依次加上缓存、MQ、分库分表和更多机器，而是：

> 将业务流量、成功语义、延迟和可用性要求，转换为整条请求链路可计算、可保护、可压测验证的容量方案。

系统容量由最弱的共享环节决定。应用实例容量充足，不代表数据库、缓存、MQ 或下游服务也能承受相同流量。

## 2. 解决的问题

1. 明确接口返回“更新成功”时，系统究竟承诺了什么。
2. 从目标 QPS 和响应时间估算在途并发与实例数量。
3. 将数据库、缓存、MQ 和下游能力换算成统一的请求容量。
4. 区分缓存、异步化、批量化、分片和扩容各自解决的问题。
5. 在突发流量超过安全容量时，通过限流、排队、隔离和降级避免雪崩。
6. 通过阶梯压测和故障演练证明方案，而不是只给出理论架构图。

## 3. 机制

### 3.1 先明确业务约束

设计前至少需要确认：

1. 目标流量是平均值、稳定峰值还是瞬时峰值。
2. 读写比例、单请求 SQL 次数、请求体和响应体大小。
3. 平均响应时间、P95 / P99、超时率和错误率目标。
4. 峰值持续时间，以及峰值结束后的正常流量。
5. 数据是否允许短暂不一致、是否允许丢弃、是否必须保持顺序。
6. 返回“更新成功”表示核心数据库事务已经提交，还是只表示请求已受理。
7. 允许故障几个实例，以及故障切换需要在多长时间内完成。

“更新成功”和“请求已受理”决定了不同的关键路径：

```text
更新成功：
请求 -> 校验与幂等 -> 核心数据库事务提交 -> 返回成功

请求已受理：
请求 -> 可靠任务记录或可靠消息提交 -> 返回已受理 -> 后台处理
```

只有非核心通知、统计、报表和允许延迟的派生数据，才能在不改变“更新成功”语义的情况下移出同步关键路径。

### 3.2 容量估算

平均在途并发可以用 Little's Law 的简化形式估算：

```text
平均并发请求数 ≈ QPS × 平均响应时间（秒）
```

例如：

```text
目标 QPS：10000
平均响应时间：100ms = 0.1s

平均并发请求数 ≈ 10000 × 0.1 = 1000
```

单实例容量不能使用压测极限值。需要通过阶梯压测找到吞吐趋平、P99、错误率或资源指标开始恶化的容量拐点，再保留安全余量。

实例数量的初始估算：

```text
最低运行实例数 = ceil(目标 QPS ÷ 单实例安全 QPS)
部署实例数 = 最低运行实例数 + 故障余量
```

例如单实例安全吞吐为 1200 QPS：

```text
最低运行实例数 = ceil(10000 ÷ 1200) = 9
若要求同时故障 2 个实例后仍可承载，则最低部署 11 个实例
部署 12 个实例时，故障 2 个后仍有 12000 QPS 安全容量
```

整条链路容量需要统一换算为请求 QPS：

```text
系统安全 QPS
= min(
    网关容量,
    应用集群容量,
    数据库安全 SQL/s ÷ 单请求平均落库 SQL 数,
    Redis安全操作数 ÷ 单请求平均 Redis 操作数,
    MQ和下游服务换算后的请求容量
  )
```

SQL 次数只适合做第一轮估算。查询与更新的成本不同，最终还要观察事务耗时、锁等待、日志和刷盘、IO、复制延迟与连接等待。

### 3.3 缓存只优化适合缓存的读路径

假设目标流量为 10000 QPS，每个请求包含一次查询和一次核心更新，查询缓存命中率为 80%：

```text
数据库查询 = 10000 × 20% = 2000 SQL/s
数据库更新 = 10000 × 1 = 10000 SQL/s
数据库总量 = 12000 SQL/s
```

计算优化后容量时，必须重新使用目标流量，不能继续以优化前系统只能承载的 QPS 为输入。

Cache Aside 常见写路径：

```text
更新数据库并提交
-> 删除缓存
-> 后续查询未命中后，从数据库重建缓存
```

先删除缓存再更新数据库，可能出现并发查询从旧数据库读取数据并重新写入缓存。更新数据库后删除缓存仍存在短暂不一致和删除失败问题，通常通过有限重试、可靠失效事件、监控和 TTL 兜底。

账户余额、支付结果等强一致核心状态不能让缓存承担权威判断。缓存可以用于展示，但真正的扣款、支付和额度判断需要以权威数据库事务结果为准。

### 3.4 写入扩展、分片与热点

只读副本能够分担查询，不能直接提升主库核心写入能力。SQL、事务和索引已经合理，单个主库写入仍不足时，才考虑按稳定业务键分片。

分片不是应用多实例后的默认动作。它会引入：

1. 分片路由和扩容迁移。
2. 跨分片查询、分页和事务。
3. 数据倾斜和热点键。
4. 每个分片的高可用与故障切换。

热点键不会随着普通分片数量增加而消失。若一个企业账户产生 3000 QPS，其余 7000 QPS 平均分布到 `n` 个分片，则热点分片至少承担：

```text
热点分片负载 = 3000 + 7000 / n
```

当 `n` 不断增加时，负载仍趋近 3000 QPS。如果这些请求更新同一行，还会产生行锁串行、连接占用和重试放大。

此时应先分析更新模型：

1. 每个请求是否必须更新同一条汇总记录。
2. 是否可以将独立订单作为核心事实逐笔写入。
3. 汇总统计是否允许异步聚合。
4. 是否存在余额不能为负等必须串行保证的业务约束。

例如支付订单必须同步提交，但商户今日收款展示允许延迟，可以将订单逐笔落库，再按商户对成功事件做秒级聚合，把每秒 3000 次热点行更新压缩为少量批次更新。真正可提现余额不能直接使用这个最终一致统计值。

### 3.5 MQ、幂等消费与 Outbox

MQ 的主要作用是：

1. 削平短时峰值。
2. 解耦非核心处理。
3. 为消费者批量处理提供入口。
4. 通过确认、重投和死信支持失败恢复。

MQ不会自动减少业务数据总量，也不能让必须提交后返回成功的核心写入凭空异步化。消费者通过批量聚合可能减少 SQL 和事务次数，但接口语义必须保持真实。

MQ通常按至少一次投递设计，因此消费者必须幂等：

```text
稳定业务事件 ID
+ 数据库唯一约束
+ 消费登记和业务更新处于同一事务
+ 数据库提交后再 ACK
```

事件 ID 应表达业务事件，而不只是订单号：

```text
eventId = orderId + eventType + statusVersion
```

消费者故障边界：

```text
提交前宕机：
事务回滚，未 ACK，MQ重新投递

提交后、ACK前宕机：
MQ重新投递，事件唯一约束阻止业务重复生效
```

生产者直接执行“提交数据库后发送 MQ”仍有双写缺口。事务型 Outbox 在同一个数据库事务中写业务记录和待发送事件：

```text
生产者事务：
支付订单 + Outbox事件

后台发送：
扫描PENDING -> 发送MQ -> Broker确认 -> 标记SENT

消费者事务：
消费事件登记 + 商户金额统计
```

Outbox保证业务成功后一定留下可恢复的发送依据，但不保证只发送一次。若消息发送成功、标记 `SENT` 前宕机，会再次发送；最终仍由消费者幂等保证只生效一次。

Outbox也有容量成本。每个业务请求新增一条 Outbox 写入时，需要重新预算数据库写入、索引、日志、扫描和归档能力。高流量场景可以评估 CDC 监听 binlog，但需要承担变更映射、延迟和基础设施复杂度。

### 3.6 限流、排队、扩容、重试和降级

超过安全容量时，应先做准入控制，避免请求进入系统后才耗尽线程和连接。

同步请求的有界队列应优先受允许排队时间约束，而不是只以 `Xmx` 为上限：

```text
队列容量初始值 ≈ 安全处理速率 × 最大允许排队时间
```

例如系统安全吞吐 12000 QPS，最多允许额外排队 200ms：

```text
队列容量 ≈ 12000 × 0.2 = 2400
```

实际配置还要按实例分配，并考虑执行中请求、任务对象大小、客户端超时、取消传播和积压清空时间。

过载治理边界：

1. 限流：在网关或服务入口按整条链路安全容量提前拒绝。
2. 排队：只吸收短时抖动，队列必须有界，不能掩盖持续过载。
3. 扩容：只有应用层是瓶颈且数据库、缓存和下游仍有余量时才有效。
4. 重试：只重试瞬时失败，必须有幂等键、最大次数、指数退避、随机抖动、总截止时间和重试预算。
5. 降级：移除统计、推荐、通知等非核心同步操作，不能伪造核心业务成功。
6. 拒绝：超过容量且不能改变语义时，快速返回明确的繁忙或限流响应，不返回“更新成功”。

如果业务要求 20000 QPS 全部成功、不能拒绝，又必须同步提交后返回，那么系统必须提前按峰值建设容量；否则只能修改接口语义为“请求已受理”。

### 3.7 压测和故障验证

阶梯压测不是只寻找极限值，而是寻找安全容量：

1. 逐档提高 QPS，并让每档持续到指标稳定。
2. 观察吞吐是否继续增长，以及 P95 / P99、错误率和超时率。
3. 观察 CPU、堆、GC、线程、队列、连接池和下游资源趋势。
4. 选择吞吐开始趋平但延迟和错误率尚未恶化的位置，并保留余量。
5. 进行长时间稳定性压测，检查内存、连接、队列和积压是否持续增长。

故障演练还需要验证：

1. 停止实例后，健康检查多久完成摘除。
2. 剩余实例流量是否均匀，P99 和错误率是否仍满足 SLA。
3. 在途请求是否丢失，客户端是否产生重试风暴。
4. 数据库连接、锁等待、Redis 和下游是否被故障流量压垮。
5. 成功响应与数据库事实是否一致，是否出现丢失和重复。
6. 实例恢复后流量、队列和连接是否平稳回落。

## 4. 边界

1. 所有容量公式都是初始估算，不能代替真实链路压测。
2. 平均响应时间适合估算平均并发，线程和连接仍需结合 P99、超时与资源模型验证。
3. 缓存适合可接受一定一致性窗口的热点读，不适合替代权威业务事实。
4. MQ削峰不等于提升数据库长期处理能力，持续流量大于消费能力仍会形成积压。
5. 分片提升不同分片之间的并行能力，不能自动消除热点业务键和同一行竞争。
6. Outbox解决业务提交与消息发送依据的原子落地，不提供端到端“只处理一次”。
7. 所有重试都会消耗容量，必须纳入过载和容量预算。

## 5. 项目或工程关联

1. 结算系统的百万级流水批处理、数据库状态抢占、批次事务和明细级 Checkpoint，可以作为异步批处理、恢复和幂等边界的真实项目证据。
2. N+1 优化和动态分区查询案例说明，数据库压力应先从 SQL 次数、访问范围和事务模型分析，而不是直接扩容。
3. 电子盖章模块的异步申请、回调幂等和超时恢复，可以用于解释核心状态与非核心异步链路。
4. 当前万级 QPS 方案属于学习和系统设计能力，不写成已经在生产承载 10000 QPS 的项目事实。

## 6. 面试表达入口

回答“如何设计 10000 QPS 且同步返回更新成功”时，按以下顺序组织：

1. 澄清目标流量、读写比例、延迟、峰值、一致性和“成功”语义。
2. 用 `并发 ≈ QPS × 响应时间` 估算在途请求，通过压测获得单实例安全吞吐并计算故障余量。
3. 只把核心事务保留在同步路径，非核心通知和统计异步化。
4. 将数据库、缓存、MQ 和下游能力统一换算为请求容量，定位最弱环节。
5. 热点读使用缓存并说明一致性；核心写先优化 SQL 和事务，必要时才分片，并检查热点键。
6. MQ只承担允许异步的削峰和批量处理，使用 Outbox、至少一次投递和消费幂等保证最终完成。
7. 入口限流、有界队列、退避重试和非核心降级保护过载。
8. 通过阶梯压测、长稳压测、实例宕机和业务一致性核对完成验证。
