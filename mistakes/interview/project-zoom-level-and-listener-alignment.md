# 项目表达的缩放层级与听众对齐

## 1. 错误表现

1. 面试官问“系统做什么”时，直接进入字段、缓存、分页或分支实现。
2. 面试官问“技术难点”时，反复回答“方案设计、综合应用、持续适配”，没有给出状态、约束、数据结构和失败路径。
3. 一个回答同时混入业务背景、系统链路、本人职责、异常补偿和多个技术机制。
4. 听众明确表示没有跟上时，继续补充更多细节，没有先退回上一层重建全貌。
5. 系统设计题中连续询问面试官现有架构和业务细节，在对方明确要求独立设计后仍没有先给出自己的默认假设与方案。
6. 回答为了覆盖所有背景、机制和边界而持续过长，面试官已经获得结论后仍继续补充同层细节。

## 2. 根因

1. 候选人熟悉大量局部细节，但没有固定项目介绍的缩放顺序。
2. 担心回答不够深入，于是在概念答案前过早加入生产案例。
3. 将“我知道很多细节”误当成“听众已经理解系统”。
4. 缺少对面试官信息状态的判断：面试官不了解领域时，业务名词本身就是认知负担。
5. 把“先澄清场景”机械化，没有区分必要约束与可以主动设定的合理假设。

## 3. 正确理解

陌生项目应按四层逐步缩放：

```text
L1 系统全貌：为谁解决什么问题，输入和输出是什么
-> L2 核心链路：三到五个关键步骤
-> L3 本人职责：负责哪一段，不负责哪一段
-> L4 代表难点：问题、约束、机制、结果和边界
```

每一层先用一到三句话建立共同上下文，再根据面试官追问进入下一层。面试官说“没理解”时，应主动退回上一层换一种更简单的表达，而不是增加更多同层细节。

系统设计题先声明两到三个关键假设并给出第一版方案；只有不同答案会实质改变设计时才继续追问。面试官要求独立设计后，应使用“我的默认假设是……因此先采用……”继续推进，而不是等待对方提供现有架构。

技术难点不能只使用“复杂、综合、抽象、适配”等评价词，需要至少包含：

1. 一个可观察的问题。
2. 一个不可违反的业务或技术约束。
3. 一个明确机制。
4. 一个结果或验证证据。

## 4. 复盘触发条件

出现以下任一情况时，立即暂停细节并重建上一层：

1. 面试官连续两次问“所以这个系统到底做什么”。
2. 面试官开始替候选人总结单据链路。
3. 面试官明确说“讲得太细”“没有跟上”“没有 get 到难点”。
4. 回答中连续出现“方案设计、综合应用、持续适配”等抽象词，却没有状态、数据、约束或结果。
5. 一个回答超过 90 秒仍未说出本人动作和结果。
6. 面试官明确反馈“表达过长”，或要求不要继续询问现有架构、直接给出个人方案。
