# 面试追问中的问题分层、知识边界与记忆压力

## 错误表现

1. 面试官指出“先查再写不原子”时，直接用“业务不会并发”防守，没有先区分单执行者、原子性和幂等。
2. 看到云数据库存储占用下降后，直接将生产现象归因于集群 MySQL 的 `DELETE` 能释放空间，混淆逻辑删除、页复用、物理文件和平台指标。
3. 面对 RAG 回答质量问题，先回答 `trace_id`、`session_id` 和会话保存，混淆可追溯性、检索相关性与生成忠实性。
4. 面试官持续追问到未知处后，只记住最后的“不会”，把知识边界误判成整场失败，并产生穷举背诵所有技术细节的压力。

## 根因

1. 现场回答先调取项目片段，没有先判断问题所在层次。
2. 没有稳定使用“已确认事实、合理推断、当前未知”的表达边界。
3. 学习内容仍以长篇知识和接口名保存，缺少少量可检索的主线关键词。
4. 将面试追问理解成“每一层都必须答到底”，忽略追问本身就是寻找能力边界。

## 正确理解

1. 先承认通用风险，再说明真实业务前提，最后给出数据库或协议层的最终兜底。
2. 生产现象可以作为证据，但不能替代机制验证；不了解的平台能力应明确标记为待确认。
3. 问题含义不清时，先确认考察层次，再回答：例如 RAG 可拆为追踪、召回、排序、生成和评测。
4. 面试准备不追求穷举背诵。每个主题先保留三到四个检索入口，再用真实项目证据和机制边界展开。
5. 被追问到不知道不等于此前回答失效；更重要的是准确说明当前边界，不为未知机制背书。

## 复盘触发条件

1. 面试官用并发、故障、重试或多实例场景挑战现有项目方案。
2. 面试官追问生产现象背后的数据库、中间件或云平台底层机制。
3. 发现自己答了熟悉的关联概念，但没有直接回答问题。
4. 面试结束后产生“需要把所有细节都背下来”或“最后不会等于整场失败”的想法。
