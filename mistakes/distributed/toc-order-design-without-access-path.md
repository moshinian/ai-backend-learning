# ToC 订单设计先说拆分技术，没有先定义用户访问路径

## 1. 错误表现

1. 面对用户历史订单查询，先提出“小表保存键值、大表读取详情”，但没有先区分订单列表和订单详情。
2. 被要求设计分库分表后，继续询问对方现有架构和业务维度，没有先给出默认分片键与路由方案。
3. 使用“配置项、管理表、分区、分库分表”等名词，但没有说明跨分片查询、扩容迁移、热点用户和历史数据的代价。
4. 回答集中在数据库结构，没有先给出峰值流量、P95 / P99、可用性、降级结果和用户体验目标。

## 2. 根因

1. 既有经验主要来自内部批处理和运营查询，习惯从数据处理任务与数据库机制出发，而不是从用户请求链路出发。
2. 把分区、索引和分库分表视为规模递增时的技术阶梯，没有先判断读写模型与路由是否匹配。
3. 澄清问题使用过多，在面试官要求独立设计后仍未主动声明合理假设。

## 3. 正确理解

ToC 订单系统应先拆访问路径：用户订单列表、订单详情、商家或运营查询。用户列表通常希望按 `user_id` 单路由并使用游标分页；订单详情需要通过带路由信息的 `order_id`、路由表或其他二级索引定位；运营跨用户查询不能假设天然单分片，需要独立的搜索、分析或汇总链路。

只有单库容量、写吞吐、存储或维护边界确实不足时才进入分库分表。设计时必须同时回答分片键、跨分片代价、热点、扩容迁移、历史冷热分层、一致性和故障降级。MySQL 分区裁剪只能排除无关分区，跨月查询仍要处理所有命中的数据，不能等同于分库后的路由隔离。

## 4. 复盘触发条件

1. 面试官给出电商、订单、用户历史记录等 ToC 场景。
2. 回答开头准备直接说分区、分库分表、路由表或缓存。
3. 被要求独立设计，却仍在追问面试官当前实现。
4. 方案没有出现列表 / 详情、分片键、SLA、分页或扩容代价。
