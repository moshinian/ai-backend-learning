# Redis 分布式锁误区

## 1. 误以为加了 Redis 锁就能绝对只处理一次

错误理解：

> `process()` 外面加 Redis 锁，就基本能保证任务只处理一次。

纠正：

Redis 锁有过期、续期失败、误删和故障切换等边界。外部 ERP 调用成功但本地未写 DONE 时，锁也无法回滚外部副作用。任务可靠性要靠数据库状态机、`process_token`、租约、业务幂等键和补偿对账。

## 2. 误以为释放锁可以直接 DEL

错误理解：

> 当前 Worker 处理完任务后直接 `DEL lock_key`。

纠正：

锁可能已经过期并被其他实例重新获取。直接 `DEL` 会误删新锁。释放锁必须用 Lua 原子判断 `unique_value` 是否匹配，匹配时才删除。

## 3. 误以为看门狗续期能证明任务健康

错误理解：

> Redis 锁还在续期，说明业务任务还正常。

纠正：

看门狗只说明续期线程还在运行。业务线程可能死循环、卡外部调用或阻塞。还要有业务心跳、任务最大执行时间、超时回收和 `process_token`。

## 4. 误以为续期不用校验锁值

错误理解：

> 看门狗只需要定期 `EXPIRE lock_key`。

纠正：

旧锁过期后，新实例可能已获得同名锁。旧 Worker 如果不校验 value 就续期，会给新 Worker 的锁续期。续期必须校验 `unique_value`。

## 5. 混淆 process_token 和业务幂等键

错误理解：

> 直接把 `process_token` 作为 ERP 幂等键。

纠正：

`process_token` 标识当前这轮处理权，每次认领都会变化。ERP 幂等键应是稳定业务身份，例如结算单 ID 或 posting 请求 ID，并绑定请求内容 hash。

## 6. 把网络超时当作外部调用失败

错误理解：

> ERP 调用超时后，本地任务可以直接标记失败。

纠正：

超时只是调用方不知道结果。ERP 可能已经成功处理。应进入不确定状态，先查询外部结果，必要时用原幂等键重试，并通过对账兜底。

## 7. 看到数据库抢占后就判断 Redis 锁完全无用

错误理解：

> 数据库已经通过条件更新抢占任务，所以项目里的 Redis 锁一定是重复设计。

根因：

只比较了实现技术，没有先确认两者保护的入口和资源范围。数据库父任务抢占只约束定时任务实例；如果同一业务还允许手工操作，手工入口可能根本不经过任务表。

正确理解：

1. 数据库条件更新限制多个同名定时任务同时取得执行权。
2. Redis 功能级锁可以协调手工操作与定时任务两个不同入口。
3. 如果 Redis 锁只包住数据库抢占 SQL，它通常是重复的；如果它保护跨入口共享业务资源，则有独立价值。
4. 无论哪种锁，都不能替代明细状态、批次事务、任务 ID 校验和业务幂等。

复盘触发条件：

1. 面试官追问“为什么数据库抢占后还要 Redis 锁”。
2. 看到系统同时存在两种互斥机制时。
3. 设计同时支持手工触发和定时执行的功能时。

## 8. 把固定 6 小时 TTL 同时当成锁租约和任务熔断

错误表现：

> 任务最长运行 6 小时，因此 Redis 锁也固定 6 小时；宕机、超时和停止都可以统一用这个时间处理。

根因：

把入口互斥、锁租约、任务健康和业务最大执行时间合成一个数字，没有分别检查持有者死亡和任务仍在运行两条时间线。

正确理解：

1. 固定 TTL 能避免永久锁，但实例很早宕机时，入口仍可能无意义地阻塞到 TTL 到期。
2. 任务正常运行超过 TTL 时，锁会提前失效，新入口可能再次进入；锁失效不等于旧 Worker 已停止。
3. Redis 锁适合保护手工与定时入口的短时互斥或抢占动作；长期执行权由数据库 owner token、租约和心跳确认。
4. 任务最大执行时间用于告警、停止和人工处置，不能自动替代锁续期与安全释放。
5. 最终数据正确性仍依赖状态条件、唯一约束、业务幂等和补偿。

复盘触发条件：

1. 锁 TTL 与任务最大执行时间被设置成同一个值。
2. 面试官追问任务宕机、执行超时或锁过期后旧实例是否还会继续写。
3. 回答开始转向心跳和任务状态，却还没有说明 Redis Key 本身何时过期、续期和释放。
